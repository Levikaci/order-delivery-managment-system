# ADR-004: PostgreSQL и версионированные миграции

**Статус:** принято (v2.0.0, issue #1)

## Проблема

SQLite-хранилище при обнаружении устаревшей версии схемы удаляло все таблицы (`DROP TABLE`), то есть обновление приложения уничтожало данные клиентов, заказов и истории. Кроме того, один файл БД и блокировка внутри процесса не позволяют запускать несколько экземпляров API.

## Решение

- Хранилище — PostgreSQL (Npgsql). Строка подключения: `ConnectionStrings:Default`.
- Схема меняется только миграциями (`src/ApiHost/Db/Migrations.cs`): версии идут подряд, применяются при старте, каждая — в своей транзакции вместе с записью в `schema_migrations`. Применённые миграции не редактируются.
- Миграции никогда не удаляют пользовательские таблицы. Неверсионированную схему, схему от более новой версии приложения и ошибку миграции приложение не «исправляет», а отказывается стартовать с понятным сообщением; при ошибке транзакция откатывается.
- Параллельный старт нескольких экземпляров сериализуется advisory-блокировкой.
- Согласованность данных — транзакции и `SELECT ... FOR UPDATE` (вместо `lock` в процессе).
- Для существующих установок — разовый перенос `tools/SqliteImport` (SQLite v2 → PostgreSQL; исходный файл только читается).

## Последствия

Требуется сервер PostgreSQL (в `docker-compose.yml` уже есть). Тесты работают на отдельной БД PostgreSQL на каждый тест (`TEST_PG_ADMIN`). Допустимое отклонение от ТЗ: в ТЗ СУБД не фиксируется, поэтому замена SQLite → PostgreSQL ему не противоречит.
