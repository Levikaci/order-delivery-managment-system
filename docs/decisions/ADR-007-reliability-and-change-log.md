# ADR-007: Единая реализация, надёжность создания заказа и журнал изменений

**Статус:** принято (v2.0.0, issue #1)

## Решения

1. **Одна реализация бизнес-логики.** Фактически используются `ApiHost.Store` + статические `*Rules` модулей. Ранние in-memory `OrderService`/`DeliveryService`/`IDeliveryService` ApiHost не использовал, они удалены вместе с тестами, которые проверяли только их. Модульная структура решения сохранена. Протоколы межмодульного взаимодействия из `contracts.md` реализованы внутри `Store` и HTTP API, а не отдельными сервисами.
2. **Создание заказа.** Заказ, позиции, история и доставка сохраняются одной транзакцией. Автоназначение курьера — отдельный шаг: его сбой не отменяет заказ, доставка остаётся `Created` и назначается повторно (сценарий 2 ТЗ). Необязательный `requestId` в `POST /api/orders` делает повтор запроса идемпотентным.
3. **Ошибки.** Необработанные исключения возвращаются в едином формате (`STORAGE_ERROR`, `INTERNAL_ERROR`, `INVALID_REQUEST`) без технических деталей.
4. **Журнал изменений заказа.** ТЗ требует только историю статусов, поэтому журнал — осознанное расширение: изменения состава, адреса и комментария пишутся в `order_changes` (старое/новое значение, время, `users.id` и имя автора); `actor_id` добавлен и в истории статусов. Просмотр: `GET /api/orders/{id}/changes`, секция «Изменения заказа» в WPF.
5. **Комментарий при `PUT /api/orders/{id}`.** Не переданный `comment` оставляет значение, пустая строка очищает (раньше любое изменение без комментария стирало его).

## Известные ограничения

Сессии хранятся в памяти; демо-пароли равны логинам; автоподбор курьера выбирает первого свободного по имени.

Сессии в PostgreSQL и балансировка курьеров добавлены в v2.1.0. Проверка содержимого повторного `requestId`, фоновое повторное назначение курьеров и разделение окружений — в v2.2.0, см. [ADR-008](ADR-008-deployment-idempotency-assignment-recovery.md).
