# ADR-008: Безопасная конфигурация, проверка повторных заказов и фоновое назначение курьеров

**Статус:** принято (v2.2.0, issue #9)

## Контекст

Повторный аудит версии 2.1.0 выявил три группы замечаний:

1. В `appsettings.json` и `docker-compose.yml` были предсказуемые пароли PostgreSQL, демо-пользователи создавались по умолчанию, порт 5432 публиковался на всех сетевых интерфейсах.
2. Повтор `POST /api/orders` с тем же `requestId`, но другими данными возвращал старый заказ и скрывал ошибку клиента.
3. После технического сбоя автоназначения доставка оставалась в `Created` до ручного вмешательства оператора.

## Решения

### 1. Окружения и проверка конфигурации

- `appsettings.json` содержит только безопасные значения: пустая строка подключения, `Seed:Demo=false`. Учебные значения (`delivery/delivery`, демо-данные) лежат в `appsettings.Development.json` и применяются только при `ASPNETCORE_ENVIRONMENT=Development` (`run.sh`, `run.bat`, профиль Visual Studio, `docker-compose.yml`).
- `StartupChecks` выполняется сразу после сборки приложения. Вне Development сервер не стартует, если: нет строки подключения; пароль PostgreSQL пустой, короче 12 символов, совпадает с логином или есть в списке стандартных (`delivery`, `postgres`, …); `Seed:Demo=true`; `Seed:OperatorPassword` слабый. Все проблемы перечисляются в одном сообщении.
- `Store` больше не подставляет строку подключения со стандартным паролем.
- Два compose-файла: `docker-compose.yml` — локальный запуск (демо-данные, порты только на `127.0.0.1`); `docker-compose.prod.yml` — рабочий (порт PostgreSQL не публикуется, БД во внутренней сети `backend`, `POSTGRES_PASSWORD` обязателен, `ASPNETCORE_ENVIRONMENT=Production`). Секреты задаются переменными окружения или файлом `.env` (шаблон `.env.example`; `.env` исключён из Git и из образа).
- Контейнер API работает от непривилегированного пользователя `app`.
- Дополнительно: сессии удалённых пользователей отзываются, сгенерированный пароль новой учётной записи — 12 случайных символов, после 5 неудачных входов логин блокируется на 5 минут (`429 TOO_MANY_ATTEMPTS`).

### 2. Идемпотентность создания заказа

- Значимые поля запроса нормализуются (`CreateOrderRequest.Fingerprint`): клиент, товары с количеством (одинаковые товары суммируются, порядок не важен), сохранённый адрес **или** введённый адрес (город, улица, дом, квартира), комментарий, признак сохранения адреса. Пробелы по краям и пустые строки не влияют — так же, как при сохранении заказа.
- SHA-256 нормализованного JSON хранится в `orders.request_hash` (миграция 0005). Сравнение отпечатков дешевле и надёжнее, чем сравнение сохранённого заказа с запросом: заказ потом может измениться через `PUT /api/orders/{id}`, а цена товара — в справочнике.
- Тот же `requestId` и тот же отпечаток — возвращается существующий заказ; другой отпечаток — `409 IDEMPOTENCY_CONFLICT`.
- Ключ действует в рамках клиента: уникальный индекс `(customer_id, request_id)` сохранён и защищает от параллельной вставки; проигравший вставку запрос перечитывает заказ и сравнивает отпечатки.
- У заказов, созданных до миграции, отпечатка нет — для них сохраняется прежнее поведение.

### 3. Фоновое назначение курьеров

- `AssignmentRetryService` (`BackgroundService`) раз в `Assignment:RetryIntervalSeconds` (по умолчанию 15 с) вызывает `Store.AssignPendingDeliveries`.
- Каждая доставка назначается в отдельной транзакции: `SELECT … FROM deliveries WHERE status='Created' AND courier_id IS NULL ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1`, затем тот же выбор курьера, что и при создании заказа (наименьшая загрузка за 24 часа, `FOR UPDATE SKIP LOCKED`). Несколько экземпляров API и ручное назначение оператором не мешают друг другу и не создают дублей: строка доставки заблокирована, повторное назначение отклоняется (`DELIVERY_ALREADY_ASSIGNED`).
- Проход заканчивается, когда нет ожидающих доставок или свободных курьеров; размер прохода — `Assignment:BatchSize`.
- При ошибке БД пауза удваивается до `Assignment:MaxBackoffSeconds` (по умолчанию 300 с), к ней добавляется небольшой случайный разброс. Ошибки не останавливают приложение; при остановке текущий проход завершается и служба выходит.
- Миграция 0006: частичный индекс очереди `ix_deliveries_pending` и уникальный индекс `ux_deliveries_active_courier` — у курьера не может быть двух доставок в статусах `Assigned`, `Accepted`, `InTransit` даже при рассогласовании `couriers.state`.
- Временными считаются `DbException`, таймауты, `SocketException` и `IOException` (`Store.IsTransient`): при остановленном контейнере БД Npgsql выбрасывает `SocketException` без обёртки.
- Отдельный брокер сообщений не используется: для текущего масштаба достаточно опроса PostgreSQL.

## Последствия

- Для рабочего запуска нужно явно задать пароли (см. README, «Рабочее развёртывание»).
- Клиенты API, которые намеренно переиспользовали `requestId` для разных заказов, получат 409 и должны генерировать новый ключ для каждого заказа (WPF-клиент так и делает).
- Миграция 0006 не применится, если в базе уже есть курьер с двумя активными доставками; такие данные нужно исправить вручную до обновления.

## Оставшиеся ограничения

- Счётчик неудачных входов хранится в памяти экземпляра API: при нескольких экземплярах лимит действует на каждый отдельно.
- Фоновое назначение не уведомляет клиента и оператора: WPF-клиент увидит назначение при очередном обновлении списка (каждые 8 секунд).
- Пароль учётной записи PostgreSQL в рабочем compose передаётся переменной окружения; для промышленной эксплуатации рекомендуется внешнее хранилище секретов (Docker secrets, Vault и т. п.).
