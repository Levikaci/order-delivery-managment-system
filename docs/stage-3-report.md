# Отчёт по этапу 3 — «Управление доставкой заказов»

## 1. Цель работы
Разработать и интегрировать взаимодействующие модули проекта через общий контракт, проверить положительный и отрицательный сценарии, использовать логирование с контекстом и подготовить автоматизированные тесты.

## 2. Средства разработки
- C# и .NET 9;
- Visual Studio;
- Git и GitHub;
- xUnit.

## 3. Состав модулей
- **Contracts** — общие типы и интерфейс взаимодействия;
- **OrderModule** — логика работы с заказом и вызов сервиса доставки;
- **DeliveryModule** — обработка запроса создания доставки;
- **ApiHost** — HTTP-точка входа приложения.

## 4. Контракт взаимодействия
Модуль заказов вызывает `IDeliveryService.CreateAsync(CreateDeliveryRequest request)`. Общий контракт находится в проекте `Contracts`, чтобы оба модуля использовали согласованные типы данных и сигнатуру метода.

## 5. Схема потока данных
```text
Клиент
  |
  v
ApiHost
  |
  v
OrderModule
  |
  | CreateDeliveryRequest
  v
Contracts / IDeliveryService
  |
  v
DeliveryModule
  |
  | результат операции
  v
OrderModule -> ApiHost -> Клиент
```

## 6. Проверяемые сценарии
1. **Положительный сценарий:** создание доставки с новым идентификатором завершается успешно.
2. **Отрицательный сценарий:** повторное создание доставки с тем же идентификатором отклоняется.

## 7. Логирование
При диагностике операций следует использовать контекстные данные, прежде всего идентификаторы заказа, клиента и доставки. Это позволяет связать сообщения журнала с конкретным запросом.

## 8. Тестирование
В решении предусмотрены проекты `OrderModule.Tests` и `Integration.Tests`. В ходе предыдущей локальной проверки в Visual Studio были показаны два успешно пройденных интеграционных теста. Перед сдачей повторно выполните из корня репозитория:

```powershell
dotnet build .\OrderDeliveryManagementSystem.sln
dotnet test .\OrderDeliveryManagementSystem.sln
```

В отчёте следует указывать результаты именно последнего запуска. Если какая-либо команда завершилась ошибкой, сначала устраните её и только потом фиксируйте успешный результат.

## 9. Организация работы в Git
Для контракта, интеграции и тестирования использовались отдельные ветки:
- `feature/stage-3-contract`;
- `feature/stage-3-integration`;
- `feature/stage-3-tests`.

Изменения интеграции отправлялись в удалённую ветку `feature/stage-3-integration`.

## 10. Проблемы интеграции и решения
- При согласовании модулей потребовалось синхронизировать поля запроса и вызов сервиса доставки.
- При слиянии веток требовалось указывать полное имя ветки `feature/stage-3-tests`.
- В одной из попыток команда `dotnet` не распознавалась в Git Bash, поэтому для проверки можно использовать Developer PowerShell/терминал Visual Studio с установленным .NET SDK.

## 11. Вывод
В рамках этапа организовано взаимодействие модулей заказа и доставки через общий контракт, предусмотрены положительный и отрицательный сценарии, а также модульные и интеграционные тесты. Финальные результаты сборки и тестирования необходимо подтвердить командами из раздела 8 перед сдачей.
