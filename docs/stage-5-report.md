# Отчёт по этапу 5 — «Инспекция кода модулей проекта»

**Курсовой проект:** «Управление доставкой заказов»  
**МДК:** 02.02 «Инструментальные средства разработки программного обеспечения»  
**Стек:** C# / .NET 9, ASP.NET Core, Git, xUnit  
**Рабочая ветка:** `feature/stage-5-code-inspection`

## 1. Цель и границы инспекции

Цель этапа — провести формализованную проверку исходного кода, определить риски, предложить корректирующие действия и сохранить воспроизводимые доказательства проверки.

Инспекция выполнена по исходникам ветки `feature/stage-4-debugging` в репозитории `Levikaci/order-delivery-managment-system`. Проверены `Program.cs`, `OrderService.cs`, `DeliveryService.cs`, контракт `IDeliveryService`, DTO `CreateDeliveryRequest`, оба тестовых проекта, `.editorconfig`, `.gitignore` и документация проекта.

Это статическая инспекция удалённого исходного кода. Команды форматирования, сборки и тестирования должны быть запущены в локальном окружении перед сдачей. Результаты этих команд в отчёте не объявляются успешными заранее.

## 3. Результаты проверки по критериям методички

| Критерий | Результат инспекции |
|---|---|
| Понятность имён | `OrderService`, `DeliveryService`, `CreateDeliveryRequest` и методы имеют понятные имена; существенных замечаний по именованию нет |
| Ответственность классов и методов | Заказ и доставка разделены, но хранение доставок встроено в `DeliveryService`; при расширении следует выделить хранилище |
| Направление зависимостей | `OrderService` зависит от `IDeliveryService`; зависимость через интерфейс упрощает тестирование |
| Дублирование логики | Существенного дублирования основной бизнес-логики не обнаружено; создание тестовых объектов повторяется в тестах |
| Обработка `null` | `DeliveryService` проверяет запрос на `null`; адрес проверяется через `string.IsNullOrWhiteSpace` |
| Валидация | В сервисах проверяются основные идентификаторы и адрес; DTO/API-граница требуют улучшения |
| Обработка исключений | Широких `catch`, скрывающих ошибки, в проверенных сервисах нет; при подключении внешнего хранилища потребуется отдельная политика ошибок |
| `CancellationToken` | В контракте и вызове сервиса отсутствует |
| Конфигурация и секреты | В просмотренном `appsettings.json` очевидных секретов не обнаружено; перед сдачей дополнительно проверить локальные файлы и историю Git |
| Внешние контракты | Есть `IDeliveryService` и `CreateDeliveryRequest`; API пока использует простые параметры, а не отдельную модель запроса |
| Наличие тестов | Есть модульные и интеграционные тесты положительных и отрицательных сценариев; расширение покрытия описано в INS-08 |
| Мёртвый и закомментированный код | Обнаружен шаблонный `WeatherForecastController`/`WeatherForecast`; назначение следует проверить и удалить, если не используется |
| `.editorconfig` | Файл присутствует; фактическое соответствие должно быть подтверждено `dotnet format --verify-no-changes` |
| Предупреждения компилятора | По просмотру исходников нельзя достоверно установить число предупреждений; нужен вывод `dotnet build` |

## 4. Инструментальная проверка

Из корня репозитория выполнить команды в терминале с установленным .NET SDK 9:

```bash
git status
git branch --show-current
git log -1 --oneline

dotnet format OrderDeliveryManagementSystem.sln --verify-no-changes
dotnet build OrderDeliveryManagementSystem.sln
dotnet test OrderDeliveryManagementSystem.sln
```

Если в окружении используется только новый формат решения `.slnx`, проверить его наличие и использовать фактический файл решения, поддерживаемый установленным SDK. Не считать команду успешной, пока не получен код завершения `0`.

Внести в отчёт фактические результаты запуска:
- `dotnet format`: [вставить итог];
- `dotnet build`: [вставить число предупреждений/ошибок];
- `dotnet test`: [вставить число пройденных/непройденных тестов].

Если форматирование не проходит, выполнить `dotnet format`, просмотреть изменения, повторно выполнить проверку и зафиксировать исправления. Если сборка или тесты завершаются ошибкой, сначала устранить её.

## 5. Воспроизводимость и Git

Для этапа используется отдельная ветка `feature/stage-5-code-inspection`. Перед началом следует сохранить исходное состояние командами `git status`, `git branch --show-current`, `git log -1 --oneline`. После добавления отчёта и исправлений проверить `git diff`, выполнить команды раздела 4 и зафиксировать результат логичным коммитом.

Рекомендуемое сообщение коммита:

```text
docs: add stage 5 code inspection report
```

Если будут исправления исходного кода или форматирования, их следует фиксировать отдельным коммитом, чтобы история показывала различие между инспекцией и корректирующими изменениями.

## 6. Оставшиеся риски и решения

В текущем прототипе основными рисками являются конкурентный доступ к in-memory хранилищу, отсутствие отмены асинхронных операций, отсутствие явной связи заказа с доставкой в DTO, упрощённый контракт API и неполное покрытие граничных сценариев.

Для учебного прототипа допустимо оставить часть замечаний открытыми, если это не противоречит требованиям преподавателя и ограничения явно описаны. Для эксплуатации с параллельными запросами необходимо устранить проблему потокобезопасности и заменить in-memory хранилище устойчивым хранилищем данных.

В ходе статической инспекции проверены именование, ответственность компонентов, зависимости, дублирование, обработка `null`, валидация, исключения, отмена асинхронных операций, конфигурация, контракты, тесты, шаблонный код и правила форматирования. Выявленные проблемы оформлены в таблице с рисками и рекомендациями.

Этап можно считать завершённым после фактического запуска инструментальных проверок, добавления их результатов в отчёт и фиксации отчёта/изменений в Git. До этого инструментальные результаты имеют статус «требует проверки», а не «успешно пройдены».
