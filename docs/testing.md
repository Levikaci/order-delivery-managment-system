# Тестовая стратегия

## До появления кода

Пока реализация отсутствует, автоматические тесты не создаются искусственно. На Этапе 1 фиксируются сценарии, которые должны быть проверены после реализации.

## Модульные тесты

Проверить:

1. создание заказа с корректными данными;
2. отказ при отсутствующем клиенте;
3. назначение свободного курьера;
4. отказ при занятом курьере;
5. допустимые переходы статусов;
6. запрет недопустимых переходов.

## Интеграционные тесты

### Успешное создание заказа

```text
ApiHost
 -> OrderModule
 -> CustomerModule
 -> DeliveryModule
 -> CourierModule
```

Ожидается создание заказа и доставки.

### Нет доступного курьера

Ожидается:

- заказ сохраняется в корректном состоянии;
- доставка остается `Created`;
- курьер не назначается;
- операция может быть повторена после появления доступного курьера.

### Завершение доставки

```text
Created -> Assigned -> Accepted -> InTransit -> Delivered
```

Ожидается корректная история статусов.

## Фактическое состояние

277 автоматических тестов (41 модульный + 236 интеграционных; `dotnet test OrderDeliveryManagementSystem.sln`, все проходят). Интеграционные тесты работают на **реальном PostgreSQL**: каждый тест создаёт и удаляет собственную базу.

Подключение к серверу — переменная `TEST_PG_ADMIN` (строка подключения с правом `CREATE DATABASE`); по умолчанию `Host=localhost;Port=5432;Username=postgres;Password=postgres;Database=postgres`. Быстрый старт: `docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres postgres:16`. В CI — service-контейнер (`.github/workflows/ci.yml`).
