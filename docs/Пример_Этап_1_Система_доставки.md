# 2. Назначение и границы проекта

## 2.1. Назначение системы

Разрабатываемая программная система предназначена для автоматизации аренды игровых приставок с доставкой клиенту.

Пользователь системы должен иметь возможность:

- просматривать доступные игровые приставки;
- получать информацию о стоимости аренды;
- выбирать период аренды;
- оформлять заказ;
- указывать адрес доставки;
- получать информацию о состоянии заказа;
- отменять заказ до начала аренды.

Сотрудник сервиса должен иметь возможность:

- добавлять и изменять игровые приставки;
- изменять доступность оборудования;
- просматривать заказы;
- подтверждать выдачу приставки;
- изменять состояние доставки;
- подтверждать возврат оборудования.

---

## 2.2. Основные объекты предметной области

В системе выделены следующие основные сущности:

- клиент;
- игровая приставка;
- модель приставки;
- заказ на аренду;
- период аренды;
- доставка;
- адрес доставки;
- состояние заказа.

Примеры игровых приставок:

- PlayStation 5;
- Xbox Series X;
- Nintendo Switch.

---

## 2.3. Границы проекта

### В систему входит

1. Ведение каталога игровых приставок.
2. Проверка доступности приставки.
3. Создание заказа на аренду.
4. Расчет предварительной стоимости аренды.
5. Резервирование приставки.
6. Создание заявки на доставку.
7. Изменение состояния заказа.
8. Регистрация возврата приставки.
9. Хранение информации о клиентах.
10. Просмотр истории заказов.

### В систему не входит

В рамках курсового проекта не реализуются:

- реальные банковские платежи;
- интеграция с банковскими системами;
- GPS-навигация курьера;
- интеграция с внешними службами доставки;
- автоматическая отправка SMS;
- мобильное приложение;
- расчет реального маршрута курьера.

Эти функции могут быть добавлены при дальнейшем развитии проекта.

# 4. Перечень модулей системы

В проекте выделено четыре основных функциональных модуля.

| Модуль | Ответственность |
|---|---|
| `CatalogModule` | Хранение информации об игровых приставках и проверка их доступности |
| `RentalModule` | Создание и управление заказами на аренду |
| `DeliveryModule` | Создание и управление доставкой и возвратом оборудования |
| `CustomerModule` | Хранение информации о клиентах |

Дополнительно используется `ApiHost`, который принимает запросы от пользовательского интерфейса и передает их соответствующим модулям.

---

## 4.1. CatalogModule

Отвечает за каталог оборудования.

Основные функции:

- получение списка приставок;
- получение информации о приставке;
- проверка доступности на выбранный период;
- резервирование приставки;
- снятие резерва;
- изменение состояния оборудования.

Пример состояний:

```text
Available
Reserved
Rented
Maintenance
```

---

## 4.2. RentalModule

Отвечает за аренду оборудования.

Основные функции:

- создание заказа;
- расчет стоимости;
- изменение периода аренды;
- подтверждение заказа;
- отмена заказа;
- завершение аренды.

Модуль взаимодействует с:

```text
CatalogModule
DeliveryModule
CustomerModule
```

---

## 4.3. DeliveryModule

Отвечает за доставку оборудования клиенту и его возврат.

Основные функции:

- создание заявки на доставку;
- хранение адреса;
- изменение состояния доставки;
- подтверждение передачи приставки;
- создание заявки на возврат.

Пример состояний:

```text
Created
Preparing
InDelivery
Delivered
Returning
Completed
Cancelled
```

---

## 4.4. CustomerModule

Отвечает за работу с клиентами.

Основные функции:

- регистрация клиента;
- получение данных клиента;
- изменение контактных данных;
- просмотр истории заказов.

# 7. Внутренние зависимости

Внутренние зависимости определяют взаимодействие проектов внутри решения.

```text
Api
 ↓
Rental
 ↓
Contracts

Api
 ↓
Catalog
 ↓
Contracts

Api
 ↓
Delivery
 ↓
Contracts

Api
 ↓
Customers
 ↓
Contracts
```

При этом бизнес-модули не должны напрямую обращаться к внутренним классам друг друга.

Взаимодействие выполняется через публичные контракты.

Например:

```text

      ↓
IConsoleReservationService
      ↓
CatalogModule
```

Это позволяет уменьшить связанность модулей.

# 10. Описание API

Клиентское приложение взаимодействует с системой через HTTP API.

Предполагаются следующие основные точки входа.

| Метод | Адрес | Назначение |
|---|---|---|
| `GET` | `/api/consoles` | Получение каталога |
| `GET` | `/api/consoles/{id}` | Получение приставки |
| `POST` | `/api/rentals` | Создание аренды |
| `GET` | `/api/rentals/{id}` | Получение заказа |
| `POST` | `/api/rentals/{id}/cancel` | Отмена аренды |
| `GET` | `/api/deliveries/{id}` | Получение информации о доставке |

Контракт API на последующих этапах может быть дополнительно описан средствами OpenAPI.

# 11. Протокол взаимодействия № 1  
## Резервирование игровой приставки

### 11.1. Инициатор и получатель

**Инициатор:**

```text
RentalModule
```

**Получатель:**

```text
CatalogModule
```

---

### 11.2. Назначение

Протокол используется при создании заказа на аренду.

Перед сохранением заказа необходимо убедиться, что выбранная приставка свободна на необходимый период, и зарезервировать ее.

---

### 11.3. Механизм вызова

Асинхронный вызов через интерфейс C#:

```csharp
IConsoleReservationService
```

Зависимость передается через механизм Dependency Injection.

---

### 11.4. Точка входа

```csharp
Task<ReserveConsoleResult> ReserveAsync(
    ReserveConsoleRequest request,
    CancellationToken cancellationToken);
```

---

### 11.5. Формат запроса

```json
{
  "consoleId": "8939af05-2a59-4758-a263-75df01c6d3f0",
  "rentalId": "4f7fb20d-b92c-4082-a031-7eb643216a18",
  "startDate": "2026-10-01",
  "endDate": "2026-10-05"
}
```

---

### 11.6. Успешный ответ

```json
{
  "success": true,
  "errorCode": null
}
```

---

### 11.7. Ошибки

Возможные ошибки:

| Код | Описание |
|---|---|
| `CONSOLE_NOT_FOUND` | Приставка не существует |
| `CONSOLE_NOT_AVAILABLE` | Приставка занята на выбранный период |
| `INVALID_RENTAL_PERIOD` | Некорректный период аренды |

Пример:

```json
{
  "success": false,
  "errorCode": "CONSOLE_NOT_AVAILABLE"
}
```

---

### 11.8. Таймаут

Операция должна завершиться не более чем за:

```text
3 секунды
```

При отмене запроса используется `CancellationToken`.

---

### 11.9. Повторная отправка

Автоматический повтор операции резервирования не выполняется.

Причина: повторный вызов без дополнительной проверки может привести к неоднозначному состоянию резерва.

Повтор операции выполняется только после проверки результата предыдущего вызова.

---

### 11.10. Аутентификация

Дополнительная аутентификация между модулями не выполняется, поскольку они работают внутри одного серверного приложения.

Проверка прав пользователя выполняется на уровне API.

---

### 11.11. Версия контракта

```text
ConsoleReservationContract v1
```

---

### 11.12. Пример обмена

```text
RentalModule
      │
      │ ReserveAsync(...)
      ▼
CatalogModule
      │
      │ Проверка приставки
      │
      │ Проверка периода
      │
      │ Создание резерва
      ▼
ReserveConsoleResult
      │
      ▼
RentalModule
```

При успешном резервировании `RentalModule` продолжает создание заказа.

При ошибке `CONSOLE_NOT_AVAILABLE` заказ не создается.


### 12.8. Таймаут

```text
3 секунды
```

Повторный запрос допускается только после проверки того, что доставка для данного заказа еще не существует.

`RentalId` используется для предотвращения создания нескольких одинаковых доставок.

### 12.10. Аутентификация

Внутренняя аутентификация между модулями не требуется.

Доступ к операции создания заказа предварительно проверяется на уровне API.

# 13. Общий сценарий создания заказа

После определения двух протоколов полный процесс создания заказа выглядит следующим образом:

```text
Клиент
  │
  │ Создает заказ
  ▼
ApiHost
  │
  ▼
RentalModule
  │
  ├──────────────► CustomerModule
  │                 Проверка клиента
  │
  ├──────────────► CatalogModule
  │                 Проверка и резервирование
  │                 приставки
  │
  │
  │ Создание Rental
  │
  └──────────────► DeliveryModule
                    Создание доставки
```

Результатом операции является созданный заказ аренды с зарезервированной приставкой и зарегистрированной доставкой.

# 15. Тестовая стратегия

## 15.1. Модульные тесты

Модульные тесты должны проверять отдельные правила предметной области.

Примеры:

### Тест 1

Приставка доступна на указанный период.

**Ожидаемый результат:** резервирование выполняется успешно.

### Тест 2

Приставка уже арендована.

**Ожидаемый результат:**

```text

```

### Тест 3

Дата окончания аренды меньше даты начала.

```text
INVALID_RENTAL_PERIOD
```

### Тест 4

Стоимость аренды рассчитывается исходя из количества дней.

**Ожидаемый результат:** рассчитана корректная итоговая стоимость.

## ADR-001. Использование модульной архитектуры

### Статус

Принято.

### Проблема

Необходимо разделить функции системы таким образом, чтобы изменение работы доставки не приводило к изменению каталога или логики клиентов.

### Решение

Разделить приложение на функциональные модули:

```text
Catalog
Rental
Delivery
Customers
```

### Причина

Такое разделение позволяет:

- определить ответственность компонентов;
- уменьшить связанность;
- независимо тестировать бизнес-логику;
- упростить последующее расширение проекта.

---

## ADR-002. Взаимодействие через контракты

### Статус

Принято.

### Проблема

Прямое обращение одного модуля к внутренним классам другого увеличивает связанность приложения.

### Решение

Взаимодействие модулей выполнять через публичные интерфейсы и DTO.

Например:

```text
RentalModule
        ↓
IConsoleReservationService
        ↓
CatalogModule
```

### Последствия

Положительные:

- модули слабее связаны;
- проще выполнять тестирование;
- контракт взаимодействия можно изменить контролируемо.

Отрицательные:

- необходимо поддерживать дополнительные DTO и интерфейсы.

# 23. Оставшиеся риски

На данном этапе выявлены следующие риски.

### Риск 1. Одновременное резервирование

Два пользователя могут попытаться арендовать одну приставку на одинаковый период.

На этапе реализации необходимо обеспечить защиту от одновременного резервирования.

### Риск 2. Ошибка после резервирования

Приставка может быть успешно зарезервирована, но создание заказа завершится ошибкой.

Необходимо предусмотреть отмену резерва.

### Риск 3. Ошибка создания доставки

Заказ может быть создан, но доставка не зарегистрирована.

Необходимо определить способ повторной обработки операции.

### Риск 4. Изменение контрактов

При изменении DTO необходимо контролировать совместимость взаимодействующих модулей.
