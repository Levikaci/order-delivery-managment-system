# 2. Назначение и границы проекта

## 2.1. Назначение системы

Программная система предназначена для автоматизации управления доставкой заказов. Система позволяет регистрировать заказы, хранить сведения о клиентах и адресах, назначать курьеров, отслеживать состояние доставки и фиксировать результат выполнения заказа.

Пользователь системы должен иметь возможность:

- создавать заказ на доставку;
- указывать данные клиента и адрес доставки;
- просматривать информацию о заказе;
- получать текущий статус доставки;
- просматривать историю изменений статуса;
- отменять заказ до передачи его в доставку.

Сотрудник или оператор системы должен иметь возможность:

- просматривать список заказов;
- назначать курьера;
- изменять статус доставки;
- изменять данные заказа;
- контролировать выполнение доставок;
- просматривать информацию о курьерах и их текущей загрузке.

Курьер должен иметь возможность:

- просматривать назначенные ему доставки;
- получать сведения о заказе и адресе;
- принимать заказ в работу;
- отмечать получение заказа;
- подтверждать доставку;
- сообщать о невозможности выполнения доставки.

## 2.2. Основные объекты предметной области

В системе выделены следующие сущности:

- клиент (`Customer`);
- заказ (`Order`);
- позиция заказа (`OrderItem`);
- адрес доставки (`DeliveryAddress`);
- доставка (`Delivery`);
- курьер (`Courier`);
- статус заказа (`OrderStatus`);
- статус доставки (`DeliveryStatus`);
- история изменения статусов (`StatusHistory`).

## 2.3. Границы проекта

### В систему входит

1. Регистрация и хранение заказов.
2. Хранение данных клиентов.
3. Хранение адресов доставки.
4. Назначение курьеров на заказы.
5. Изменение статусов заказов и доставок.
6. Просмотр текущего состояния доставки.
7. Ведение истории изменения статусов.
8. Поиск и просмотр заказов.
9. Контроль доступности курьеров.
10. Формирование основных сведений о выполненных доставках.

### В систему не входит

В рамках курсового проекта не реализуются:

- реальные банковские платежи;
- интеграция с банковскими системами;
- автоматическая GPS-навигация курьера;
- построение оптимального маршрута в реальном времени;
- интеграция с внешними картографическими сервисами;
- автоматическая отправка SMS через реального оператора связи;
- полноценное мобильное приложение курьера;
- интеграция с внешними маркетплейсами.

Эти функции могут быть добавлены при дальнейшем развитии проекта.

# 4. Перечень модулей системы

В проекте выделены следующие основные функциональные модули:

| Модуль | Ответственность |
|---|---|
| `OrderModule` | Создание, изменение и просмотр заказов |
| `DeliveryModule` | Создание и управление доставками, отслеживание их статусов |
| `CourierModule` | Хранение данных курьеров и управление их доступностью |
| `CustomerModule` | Хранение информации о клиентах и адресах |
| `ApiHost` | Приём HTTP-запросов и предоставление API клиентским приложениям |

---

## 4.1. OrderModule

Отвечает за жизненный цикл заказа.

Основные функции:

- создание заказа;
- получение заказа по идентификатору;
- изменение состава и данных заказа;
- отмена заказа;
- изменение статуса заказа;
- просмотр истории заказа.

Пример статусов заказа:

```text
Created
Confirmed
Preparing
InDelivery
Delivered
Cancelled
```

---

## 4.2. DeliveryModule

Отвечает непосредственно за организацию доставки.

Основные функции:

- создание доставки для заказа;
- назначение курьера;
- изменение статуса доставки;
- фиксация времени начала и окончания доставки;
- подтверждение получения заказа клиентом;
- регистрация причины неудачной доставки.

Пример статусов доставки:

```text
Created
Assigned
Accepted
InTransit
Delivered
Failed
Cancelled
```

---

## 4.3. CourierModule

Отвечает за данные курьеров и их доступность.

Основные функции:

- регистрация курьера;
- получение данных курьера;
- изменение контактных данных;
- изменение статуса доступности;
- получение списка свободных курьеров;
- просмотр назначенных доставок.

Пример состояний курьера:

```text
Available
Busy
Offline
Blocked
```

---

## 4.4. CustomerModule

Отвечает за работу с клиентами и адресами.

Основные функции:

- регистрация клиента;
- получение информации о клиенте;
- изменение контактных данных;
- добавление и изменение адресов;
- получение адреса доставки по идентификатору.

---

## 4.5. ApiHost

`ApiHost` является точкой входа для внешних клиентов системы.

Он отвечает за:

- обработку HTTP-запросов;
- проверку входных данных;
- аутентификацию пользователей;
- маршрутизацию запросов к соответствующим модулям;
- формирование HTTP-ответов;
- возврат ошибок в едином формате.

Для проекта используется модульная архитектура с API-слоем.

```text
                         ┌────────────────────┐
                         │      Клиент        │
                         │ Web / API Client   │
                         └─────────┬──────────┘
                                   │ HTTP/JSON
                                   ▼
                         ┌────────────────────┐
                         │      ApiHost       │
                         │   ASP.NET Core     │
                         └─────────┬──────────┘
                                   │
             ┌─────────────────────┼─────────────────────┐
             │                     │                     │
             ▼                     ▼                     ▼
      ┌───────────────┐    ┌────────────────┐    ┌────────────────┐
      │  OrderModule  │    │ DeliveryModule │    │ CustomerModule │
      └───────┬───────┘    └───────┬────────┘    └────────────────┘
              │                    │
              │                    ▼
              │             ┌───────────────┐
              └────────────►│ CourierModule │
                            └───────────────┘
              │
              ▼
       ┌─────────────────┐
       │   Persistence   │
       │ Database / ORM  │
       └─────────────────┘
```

Основной поток создания доставки:

```text
Клиент
  │
  │ POST /api/orders
  ▼
ApiHost
  │
  ▼
OrderModule
  │
  ├──────────────► CustomerModule
  │                 Проверка клиента и адреса
  │
  └──────────────► DeliveryModule
                    Создание доставки
                           │
                           ▼
                    CourierModule
                    Назначение курьера
```

# 7. API и контракты

Внешнее взаимодействие с системой выполняется по HTTP с использованием JSON.


| Метод | Endpoint | Назначение |

# 10. Тестовая стратегия

Для проекта предусматриваются три уровня проверки.

## 10.1. Модульные тесты

Проверяются отдельные правила бизнес-логики.

Примеры:

1. Создание заказа с корректными данными — операция выполняется успешно.
2. Создание заказа без клиента — возвращается ошибка валидации.
3. Назначение свободного курьера — курьер получает статус `Busy`.
4. Назначение занятого курьера — операция отклоняется.
5. Изменение статуса доставки на `Delivered` — доставка завершается успешно.
6. Изменение статуса из недопустимого состояния — возвращается ошибка.

## 10.2. Интеграционные тесты

Проверяется взаимодействие модулей.

### Сценарий 1. Создание заказа и доставки

```text
ApiHost
   ↓
OrderModule
   ↓
CustomerModule
   ↓
DeliveryModule
   ↓
CourierModule
```

Ожидается:

- заказ создан;
- клиент и адрес проверены;
- доставка создана;
- доступный курьер назначен.

### Сценарий 2. Нет доступного курьера

Ожидается:

- заказ сохраняется;
- доставка получает состояние `Created`;
- курьер не назначается;
- система возвращает понятный результат для повторного назначения.

### Сценарий 3. Успешное завершение доставки

```text
Created → Assigned → Accepted → InTransit → Delivered
```

Ожидается корректное изменение статусов и сохранение истории.

## 10.3. Проверка сборки

После внесения изменений выполняются:

```bash
dotnet build
dotnet test
```

Критерий успешной проверки — отсутствие ошибок сборки и прохождение автоматических тестов.

# 13. Протокол взаимодействия №1 — создание доставки

## 13.1. Инициатор и получатель

**Инициатор:** `OrderModule`  
**Получатель:** `DeliveryModule`

## 13.2. Назначение

Создание записи о доставке после успешного оформления заказа.

## 13.3. Транспорт или механизм вызова

Внутренний вызов сервиса через интерфейс приложения. На внешнем уровне операция доступна через HTTP API.

## 13.4. Точка входа

Внутренний контракт:

```text
IDeliveryService.CreateAsync(CreateDeliveryRequest request)
```

HTTP-точка входа:

```http
POST /api/deliveries
```

## 13.5. Формат запроса

```json
{
  "orderId": "a6f3f77e-3d61-4d3f-a0a2-0f58f5d6a4b1",
  "customerId": "8f3f7b9c-5a51-4df7-8c0d-5e9f1d4c2a10",
  "address": {
    "city": "Волгоград",
    "street": "Мира",
    "house": "15",
    "apartment": "24"
  }
}
```

## 13.6. Формат успешного ответа

```json
{
  "deliveryId": "c8b4d8de-1d2a-4e2f-9f8c-9a3d2f8f1b32",
  "orderId": "a6f3f77e-3d61-4d3f-a0a2-0f58f5d6a4b1",
  "status": "Created"
}
```

## 13.7. Ошибки и их представление

| Код | Описание |
|---|---|
| `ORDER_NOT_FOUND` | Указанный заказ не найден |
| `CUSTOMER_NOT_FOUND` | Клиент не найден |
| `INVALID_ADDRESS` | Адрес заполнен некорректно |
| `DELIVERY_ALREADY_EXISTS` | Для заказа уже существует доставка |

Пример:

```json
{
  "success": false,
  "errorCode": "DELIVERY_ALREADY_EXISTS",
  "message": "Для указанного заказа доставка уже создана"
}
```

## 13.8. Таймаут

Максимальное ожидаемое время выполнения — **3 секунды**.

## 13.9. Правила повторной отправки

Повторная отправка допускается при временной ошибке. Для защиты от создания дубликатов используется `orderId` и проверка существующей доставки.

## 13.10. Аутентификация

Внутренний вызов разрешён только авторизованным компонентам приложения. Для внешнего HTTP API используется аутентификация пользователя.

## 13.11. Версия контракта

```text
DeliveryContract v1
```

```text
     │ Проверка заказа и адреса
```

# 14. Протокол взаимодействия №2 — назначение курьера

## 14.1. Инициатор и получатель

**Инициатор:** `DeliveryModule`  
**Получатель:** `CourierModule`

## 14.2. Назначение

Поиск доступного курьера и назначение его на конкретную доставку.

## 14.3. Транспорт или механизм вызова

Внутренний вызов сервиса через интерфейс приложения.

## 14.9. Правила повторной отправки

## 14.10. Аутентификация

## ADR-001. Использование модульной архитектуры

**Статус:** принято.

**Проблема:** необходимо разделить работу с заказами, доставками, курьерами и клиентами.

**Решение:** выделить `OrderModule`, `DeliveryModule`, `CourierModule` и `CustomerModule`.

**Причина:** разделение ответственности уменьшает связанность компонентов и упрощает тестирование.

## ADR-002. Использование DTO для обмена данными

**Статус:** принято.

**Проблема:** передача внутренних доменных объектов между модулями создаёт сильную связанность.

**Решение:** использовать отдельные DTO и контракты запросов/ответов.

**Причина:** изменения внутренней реализации модуля не должны автоматически изменять внешний контракт.

## ADR-003. Хранение истории статусов доставки

**Статус:** принято.

**Проблема:** необходимо знать не только текущий статус, но и историю выполнения доставки.

**Решение:** создавать запись `StatusHistory` при каждом значимом изменении статуса.

**Причина:** это позволяет контролировать последовательность выполнения доставки и анализировать ошибки.

# 19. Оставшиеся риски

### Риск 1. Одновременное назначение курьера

Два оператора могут одновременно назначить одного свободного курьера на разные доставки. При реализации необходимо предусмотреть проверку и защиту от конкурентного изменения состояния.

### Риск 2. Ошибка после создания заказа

Заказ может быть создан, а создание доставки может завершиться ошибкой. Необходимо предусмотреть корректную обработку такого сценария.

### Риск 3. Ошибка назначения курьера

Курьер может стать недоступным между моментом выбора и фактическим назначением. Перед сохранением назначения требуется повторная проверка его состояния.

### Риск 4. Некорректная последовательность статусов

Необходимо ограничить переходы между статусами, чтобы, например, завершённая доставка не могла снова перейти в состояние `InTransit`.

### Риск 5. Изменение контрактов

При изменении DTO и API необходимо обновлять документацию и версию соответствующего контракта.
